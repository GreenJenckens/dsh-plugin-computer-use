### P4 — Least privilege для субагентов (1 день)

**Вердикт: ДЕЛАЕМ СЕЙЧАС.** DSH-API проверен: `ctx.tools.restrict` существует,
у child есть `delegationDepth`, `toolFilter` живёт в preset-композиции. Но плагин не может
заставить чужую композицию вызвать `restrict` — значит, нужен **собственный гейт**.

**Что делаем:**
- конфиг плагина `subagents: 'deny' | 'allow'`, **default `deny`** (security fix, отмечаем
  в CHANGELOG как изменение поведения);
- в `execute` до `host.enqueue`: `depth = session.header.delegationDepth ?? options.subagentDepth`;
  при `depth >= 1` и `deny` — ошибка `computer is disabled for subagent sessions
  (delegationDepth=1); the parent session must perform desktop actions, or set subagents:"allow"`;
- audit-строка `denied-subagent` (в `%TEMP%\dsh-cu\audit.jsonl`), без аргументов;
- README: рецепт для composition/preset — `toolFilter: { deny: ['computer'] }` как
  второй слой (убирает схему из child-запроса, экономит токены);
- тесты: fake exec depth 0/1/2; интеграционный — реальный child просит `windows.list`
  и получает отказ (если subagent-тул доступен; иначе unit + документированный ручной прогон).

**Acceptance:** parent 1/1 allowed, child 1/1 denied с внятным текстом, 0 запусков
bridge для denied, schema не изменилась, overhead < 1 ms, README/SECURITY описывают
default и opt-in.

**Метрики:** 0 child desktop-ops; 1 шаг до отказа; tokens +0 (схема), latency +<1 ms;
в composition с `toolFilter` — экономия схемы ~650 tok на child-запрос.

**Откладываем:** «sandbox-гейт» на уровне ОС (отдельный low-privilege пользователь/VM) —
это deployment-рекомендация, не код плагина.

### P5 — Retention: temp и attachment-store (1 день)

**Вердикт: ДЕЛАЕМ ПОЛИТИКУ И ИНСТРУМЕНТ, НЕ ДЕЛАЕМ AUTO-GC.** DSH-документация прямо
говорит: attachments хранятся вечно, GC отложен, resumed/forked сессии могут делить объекты.
Плагин не имеет refcount-API и не должен удалять чужие объекты «на глаз».

**Что делаем:**
- plugin temp: вынести 2 ч/150 PNG в конфиг `retentionHours` / `maxFiles` (сейчас хардкод),
  тест на очистку по возрасту и по количеству;
- `scripts/prune-attachments.ps1` (вне рантайма плагина): dry-run по умолчанию,
  `-Apply`, `-OlderThanDays 30`, `-DshHome`; собирает referenced `sha256:<hash>` из
  `$DSH_HOME/sessions` (и других текстовых сторов, кроме `attachments`), удаляет только
  объекты **без ссылок и старше порога**, с path-guard «внутри objects»; JSON-отчёт;
- SECURITY/README: политика «screenshots = sensitive; temp 2 ч; attachments — вечные,
  чистить вручную/по расписанию; не удалять объекты, на которые ссылаются сессии»;
- тест на синтетическом store: referenced old, unreferenced old, unreferenced new;
  dry-run 0 удалений; apply удаляет только B; повторный запуск идемпотентен.

**Acceptance:** 0 referenced-объектов удалено; dry-run безопасен; age-порог соблюдён;
path-guard; отчёт JSON; temp-тест 2 ч/150 зелёный; политика в docs.

**Метрики:** на фикстуре удалён ровно 1 объект; 0 false deletes; prune 1 000 объектов ≤ 2 s;
temp cleanup 0 ошибок.

**Откладываем:** upstream GC в DSH, авто-удаление по расписанию внутри плагина,
шифрование/перемещение store — это отдельный продукт/политика DSH.

## 5. Что откладываем — и почему (явно)

| Отложено | Почему | Revisit trigger |
|---|---|---|
| Реальная hardware-матрица 2 монитора / 125 / 150% | На машине 1×1920×1080@96; непроверенные assertions хуже отсутствия | Появился второй монитор/150% профиль |

## 6. Риски и решения

| Риск | Вероятность | Влияние | Решение |
|---|---|---|---|

## 8. Конфликт с `docs/v0.4-scope.md` — как решаем

`docs/v0.4-scope.md` (Alex/PM, 04.11.2026) предлагает M1–M5: human gate, stable refs,

контракт: M1 вместо P6/P5. Это решение за тобой.
