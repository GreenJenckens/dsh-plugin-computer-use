## 2. Parity scorecard

Bar: "not worse than Anthropic computer use / OpenAI CUA on Windows desktop." Scored on the six dimensions the brief names.

| Dimension | Anthropic CU | OpenAI CUA | DSH v0.3 | Verdict |
|---|---|---|---|---|
| **Observation** | screenshot/step, model reads pixels | screenshot + text | UIA tree **with rects** + screenshot + OCR | **Exceeds** on structure; **trails** on stable handles |
| **Actions** | move/click/type/key/hold_key/scroll/drag, image-scaled coords | click/scroll/type/keypress/drag/wait, 0–1000 grid, `batch` | 39 actions incl. semantic `invoke`/`setvalue`/`toggle`/`select` | **Exceeds** on semantics; **trails** on batching + normalized coords |
| **Safety** | confirmation for consequential actions | takeover mode, explicit confirm set (login, payment, CAPTCHA, 2FA) | redaction, launch deny-list, audit — **no human gate** | **Materially behind** |
| **DX** | 1 tool | 1 tool, typed outputs | 1 tool, skill fallback, compact text | **At parity** on shape, behind on handles/errors |
| **Cost** | ~550 tok fixed | ~600 tok fixed | ~900 tok fixed, no tree budget | Mixed: higher fixed, lower per-step |
| **Distribution** | hosted API, versioned | hosted API, versioned | `install.ps1` + `build.json`; **no git, no CI, no tag** | **Materially behind** |

**Where we can win, and should**: Anthropic and OpenAI both drive the desktop *blind through pixels*. We have a real accessibility tree with geometry. That is a structural advantage — but v0.3 doesn't cash it in, because the model can't hold a stable reference to a node across two calls. Fixing that is the highest-leverage thing in this release.

**What we accept as permanently behind**: model-side visual grounding quality. That's the LLM's capability, not the plugin's. We compete on the harness, not on the weights.

## 3. The five must-haves

Max five, by design. Each is here because a *named competitor capability* has no counterpart in v0.3, or because a verified baseline defect blocks shipping. Everything else is in §4.

---

### M1 — Human-in-the-loop control plane *(safety)*

**Problem.** v0.3 can type into a payment field, submit an order, or close a window with unsaved work, and there is no mechanism anywhere in the stack to require a human. Anthropic's CU treats confirmation for consequential actions as table stakes; OpenAI's CUA ships an explicit takeover mode and a confirm-set. We have none. `SECURITY.md` is admirably honest that approval is "model-controlled and not a control" — the correct fix is to make the *plugin* deterministic about risk classes, not to ask the model nicely.

**What ships.**
- A **risk-class policy file** (`policy.json`, plugin-owned, not model-writable) with three classes: `A` read-only observation, `B` reversible mutation (click, scroll, type into ordinary fields, window move), `C` consequential (submit/send/purchase, password fields, `launch`, `windows.close` with a dirty-document heuristic, anything targeting an elevated process).
- Class **C** does not execute by default. It returns `needs_confirmation` with a machine-readable summary of what would happen, and only executes when the session was explicitly started with `--allow-class-c` or the user answers a DSH question that the *plugin* raises.
- `takeover` action: suspends automation, tells the human "your turn", waits bounded, then resumes — the handoff primitive OpenAI exposes for CAPTCHA/2FA.
- `ctx.tools.restrict({ deny: ['computer'] })` applied by default to **subagent scopes**, with an opt-in override.

**User-visible acceptance criteria.**
- [ ] A call that would submit a web form returns `needs_confirmation` and the UI state is provably unchanged (screenshot before/after identical) when the human declines.
- [ ] With `--allow-class-c`, the same call executes and is tagged class C in `audit.jsonl`.
- [ ] `takeover` returns within its `ms` budget whether or not the human acts, and the caller can tell which happened.
- [ ] A subagent attempting `computer` gets a clear denial naming the restriction, not a generic host error.
- [ ] Typing into any `IsPassword`-flagged field is class C *regardless of policy file contents* — the clamp cannot be edited away at runtime.

**Success metrics.** Class-C actions executed without confirmation: **0** (hard gate, not a target). Every class-C decision appears in `audit.jsonl` with its outcome: **100%**.

**Effort.** 2 eng-weeks. **Confidence** ~75% that class C can be detected accurately without app-specific adapters — that's the risk (see §6).

---

### M2 — Stable element references + bounded observation budget *(observation, cost, DX)*

**Problem.** Two verified defects. (a) `i=N` in the tree is a per-walk ordinal recomputed every call (`bridge.ps1:392-404`), so `i=7` from call N can be a different element at call N+1 — the model cannot safely reference what it saw. It must re-quote names or fall back to blind pixel clicks, which discards our one structural advantage over Anthropic/OpenAI. (b) `Get-CuTree` walks up to 4,000 nodes with no token budget, so a heavy app can blow the context window in one call.

**What ships.**
- Tree rows gain a **`ref`** — a short stable handle (`e1a3`) derived from a fingerprint of `runtimeId | automationId | role | tree path`, held in a per-window ref table with a TTL. `act.*` accepts `ref=` as a first-class selector.
- **Staleness detection**: if the element behind a ref has been destroyed, reparented, or moved window, the action fails with `stale ref e1a3 — re-run observe.tree` instead of acting on the wrong node.
- **Token budget** on `observe.tree`: `maxTokens` (default ~1,200) with deterministic truncation — deepest, offscreen, and geometry-less rows dropped first, and an explicit `… N rows elided; narrow with maxDepth/controlType` trailer so the model knows what it didn't see.
- Image-linked geometry: refs offered as click targets map to the *same* origin/scale already returned by `screenshot`, so visual and structural grounding agree.

**User-visible acceptance criteria.**
- [ ] `observe.tree` → `act.click ref=…` works in one hop on a Notepad and a browser target with no name re-quoting in the call.
- [ ] After closing and reopening the same window, a stale ref errors instead of clicking a neighbouring control.
- [ ] A 4,000-node app returns in-budget text plus an elision trailer naming the count dropped.
- [ ] Existing name/automationId selectors keep working unchanged — no breaking change for v0.3 callers.
- [ ] `ref` round-trip adds < 15% to `observe.tree` payload size.

**Success metrics.** Tree payload p95 ≤ 1,200 tokens (baseline: unbounded, up to ~4,000 nodes). Wrong-element clicks in the eval suite (M4): **0**. Median actions-to-completion on tree-targetable tasks: **−25%** vs v0.3 baseline.

**Effort.** 1.5 eng-weeks. **Confidence** ~80% — fingerprint stability is the known unknown (some apps reuse `RuntimeId`).

### M3 — Atomic action sequences + normalized coordinates *(actions, cost)*

**Problem.** OpenAI CUA batches actions per step; we require one tool call per action, so a 12-step form fill costs 12 model round trips — the dominant cost and latency term, worse than either competitor. Separately, our coordinates are raw physical pixels with no normalization, so the model must do arithmetic against `screenshot`'s origin/scale and gets it wrong under DPI scaling or multi-monitor offsets.

**What ships.**
- **`act.sequence`** — an ordered array executed atomically in one call: each step runs, its post-condition is checked (`expect: {ref|text|window}` with a bounded settle wait), and the first failure stops the sequence and returns the steps completed plus the failing step's observation. One call in, one observation out.
- **Optional normalized coordinates**: `coordSpace: "norm"` accepts `x,y ∈ [0,1000]` on the screenshot's frame and maps to physical pixels using the same origin/scale the screenshot reported. Raw-pixel behavior stays the default for compatibility.
- **Post-condition settle** replaces fixed `ms` sleeps where possible: wait until the target ref's text/geometry or the foreground window actually changes, with a hard timeout.

**User-visible acceptance criteria.**
- [ ] A 6-step form (type name → tab → type email → toggle → click submit) completes in **one** tool call, and returns either success or the exact failing step with a fresh observation.
- [ ] A sequence that hits a class-C step stops *before* it and reports `needs_confirmation` for that step only; prior steps remain committed and are listed.
- [ ] `coordSpace:"norm"` click on the centre `(500,500)` lands inside the same element as the raw-pixel click on that element's centre, at 100% and 150% DPI.
- [ ] Sequencing a single step behaves identically to the equivalent standalone action (no semantic drift).
- [ ] A failing step never leaves the host wedged: the next call succeeds.

**Success metrics.** Model round trips per task: **−50%** on multi-step tasks (eval-measured). Tokens per completed task: **−30%**. Sequence-level flake on the eval suite: **≤ 5%**.

**Effort.** 1.5 eng-weeks. **Confidence** ~70% on the settle heuristics — "wait until changed" is where desktop automation usually gets flaky, and the DPI assertions need a 150% environment we don't currently have (see §5 risk).

---

### M4 — Graded task eval suite as the release gate *(proof of parity)*

**Problem.** 19 unit tests prove the host doesn't deadlock, the deny-list denies, and passwords are redacted. They prove **nothing** about whether an agent can actually finish a task. The only end-to-end check is one smoke scenario (calculator 7×8=56). Claiming "not worse than Anthropic/OpenAI" on that evidence would be unfounded — and we cannot ship v0.4 against a bar we can't measure.

**What ships.**
- **~20 scripted desktop tasks** with automatic, non-visual verification (read the app's own state, not a screenshot): calculator arithmetic incl. a Cyrillic-named result; Notepad type + save + reopen + content compare; Windows Settings toggle and read-back; open/save file dialog navigation; browser form fill + submit + URL assertion; Excel cell entry + formula result; PDF/scan text via OCR where the app has no UIA text; a background-window task via `capture:print`; a password-field task asserting redaction; a class-C confirm-refusal task; a stale-ref recovery task.
- **Runner** emitting a JSON + markdown report: per-task pass/fail, steps, wall time, tokens where available, and a `--repeat N` mode for flake measurement.
- **CI wiring**: suite runs on every push; a regression turns the build red.

**User-visible acceptance criteria.**
- [ ] `npm run eval` runs the full suite unattended on a clean desktop and exits non-zero on any failure.
- [ ] Each task's verification reads application state (control value, file content, URL) — **no** task passes by matching pixels or by "the call returned ok".
- [ ] The report names, per task, the failing step and the observation at failure.
- [ ] `--repeat 3` yields a flake report; any task flaking above threshold fails the run.
- [ ] Total runtime ≤ 10 min so it can gate every push.

**Success metrics.** pass@1 **≥ 80%** (16/20) at release, with the four hardest documented as known-fail rather than hidden. Flake **≤ 5%** over 3 repeats. Suite wall time **≤ 10 min**.

**Effort.** 2 eng-weeks (parallelizable with M1–M3). **Confidence** ~65% — this is the item most likely to overrun, because writing *self-verifying* desktop tasks is fiddly and machine-dependent. It is also the item I'd cut last: without it, "release" is an opinion.

### M5 — Release integrity & distribution *(distribution, DX)*

**Problem.** Verified defects, not vibes: **no git repository at all** (no diffs, no tags, no rollback, no review); the live mount reports `buildHash: "unknown"` — we literally cannot prove which build is running; `build.json` is excluded from `package.json` `files`, so a packed install loses the manifest the runtime reads; and `CuCommon.ps1` exists as two drifting copies (13,735 B vs 15,151 B) with tests covering only the plugin one.

**What ships.**
- `git init` with a tagged `v0.4.0`, a `.gitignore` (`node_modules`, build output, `%TEMP%` artifacts), and the v0.3 tree as the baseline commit so this release has a reviewable diff.
- `build.json` added to `files`; **runtime assertion** — if `buildHash` resolves to `unknown`, the plugin logs a loud warning and the `mounted.json` marker is written by `install` (not by the booted process), so staleness is detectable rather than silent.
- **Single source of truth for the PS scripts**: plugin `lib/scripts/` is canonical; the skill fallback either imports it or is clearly marked frozen + hash-pinned, with a test asserting the pinned hash.
- **CI** (GitHub Actions or local pre-commit hook if there's no remote yet): `npm test` + `npm run eval` + `install -Verify`.
- **Documented rollback**: restore the previous install from the backup dir `install-plugin.ps1` already keeps, and a tested one-liner to re-pin v0.3.

**User-visible acceptance criteria.**
- [ ] `git log --oneline` shows a baseline commit and a `v0.4.0` tag; `git diff v0.3.0..v0.4.0` is reviewable.
- [ ] Fresh install → `mounted.json` shows the real `buildHash`, matching `build.json` and the tag.
- [ ] `install-plugin.ps1 -Verify` passes on a clean install and **fails** when one shipped file is mutated by a single byte.
- [ ] A test fails if the skill fallback's `CuCommon.ps1` drifts from its pinned hash.
- [ ] Rollback to v0.3 restores a working mount, verified by `npm test` + one smoke task.

**Success metrics.** Reproducible install from tag on a clean machine: **100%** (2/2 attempts). `buildHash` present and matching in `mounted.json`: **always**. Untested duplicated source files: **0**.

**Effort.** 0.75 eng-week. **Confidence** ~90%.

**Total**: ~7.75 eng-weeks ≈ **2 calendar weeks with 2 engineers**. Fits the ≤8-week discovery-to-ship bar with room for the eval suite to overrun — which it will.

## 4. Deferred — and why

Saying no publicly is the point of this section.

| Deferred | Why not in v0.4 | Revisit trigger |
|---|---|---|
| Multi-monitor & DPI≠100% **test matrix** | No environment on this box to validate; shipping untested assertions is worse than none. M3 ships the *mechanism*, not a hardware matrix. | A second monitor or a 150% profile appears on the build machine. |
| UAC / lock screen / elevated apps | Needs a signed, elevated helper service — a security project of its own. | A customer task requires interacting with an elevated app. |
| Visual grounding (template match, anchor detection, screenshot diffing) | Our tree already beats pixels where UIA exists; the pixel path is the model's job. Lowest value per eng-week. | OCR+tree fail rate > 20% on the eval suite. |
| Native clipboard read/write action | Already partly covered by `gettext clipboard=true` with buffer restore. A full clipboard API widens the secret-leak surface for little gain. | Users ask to move data between apps with no UIA. |
| Video/trajectory export & replay UI | Debugging nicety. `audit.jsonl` + the eval report cover the need. | A bug takes >1 day to reproduce from logs. |
| Per-app adapters (Excel object model, browser CDP) | Real leverage, but it's a product line, not a release item, and it dilutes the "one generic tool" thesis. | A vertical customer segment appears. |
| MCP server wrapper / non-DSH distribution | Different distribution story; don't split focus during a parity release. | The plugin is stable and someone asks for Claude Desktop/other hosts. |
| Telemetry & usage analytics | Privacy-sensitive for a desktop-control tool, and we have no consented channel. | A hosted/team deployment exists. |
| OCR language packs beyond ru/en | YAGNI until a non-ru/en user appears. | A user request naming a language. |
| Linux/macOS backends | The brief scopes Windows. Different UIA-equivalent stacks entirely. | Explicit cross-platform mandate. |
| `input.hold_key`-style chord-with-duration primitives | `input.hotkey` + `input.key` cover observed cases; `hold_key` adds state-machine complexity for rare drag-select gestures. | Eval suite shows chord-mutation tasks failing. |

## 5. Release definition — v0.4.0

v0.4.0 ships **only** when every gate below is green. No partial credit, no "we'll fix it in .1".

**Hard gates**
1. **Tests**: `npm test` 19/19 (unchanged) **plus** new unit coverage for M1 policy classes, M2 ref staleness, M3 sequence stop-on-failure.
2. **Eval**: `npm run eval` pass@1 **≥ 80%** (16/20), flake **≤ 5%** over `--repeat 3`, runtime **≤ 10 min**. The 4 permitted failures are named in the release notes.
3. **Safety**: class-C-without-confirmation count **= 0** across the whole eval suite; the confirm-refusal and password-redaction tasks pass.
4. **Integrity**: `install-plugin.ps1 -Verify` green on a clean install; `mounted.json` `buildHash` matches `build.json` and the `v0.4.0` tag.
5. **Docs**: `CHANGELOG.md` 0.4.0 entry; `SECURITY.md` updated to describe the control plane *and* honestly restate what still cannot be enforced; `README.md` limitations refreshed; `docs/v0.4-scope.md` (this file) committed.
6. **Rollback**: v0.3 restore path executed once, successfully, and recorded.

**Artifact**: tagged `v0.4.0` runnable from the repo, `build.json` shipped, install + verify in one command.

**Distribution decision**: repo-and-script install stays. We do **not** publish to npm in v0.4 — package-shape work is deferred, and an unpublished tag is a smaller liability than a bad published one. (Judgment call on thin evidence; ~60% confidence. Flag for revisit in v0.5.)

**What "not worse than Anthropic/OpenAI" means here, precisely**: parity on the six dimensions in §2, with M1 closing the only *material* deficit and M2/M3 establishing a structural lead where the tree gives us an edge. We will **not** claim benchmark parity against their hosted models — we can't run them on this box, and pretending otherwise would be the kind of claim that gets a product team distrusted. The eval suite is our evidence, and it's our own bar.

## 6. Risks & open questions

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Class-C misclassification blocks legitimate work (false positives) | High | High | Ship an audit-only "dry run" mode first; tune on the eval suite before defaulting to deny. |
| `ref` fingerprints unstable in apps that recycle `RuntimeId` | Medium | High | Fall back to name+automationId+geometry fingerprint; stale-ref error is always safe (fail closed). |
| Eval suite flakiness on a shared developer desktop | High | High | Dedicated clean VM or a documented clean-desktop procedure; `--repeat` gate catches it. |
| DPI/normalized-coord assertions untestable without a second environment | High | Medium | Ship raw-pixel default; treat norm mode as opt-in and label it beta in docs. |
| The confirm gate is illusory under `approval: never` | Medium | Critical | Enforcement lives in the plugin's policy file + subagent denial, **not** in a model-facing prompt. Verify by test that decline leaves state unchanged. |
| Scope creep from deferred items re-entering mid-sprint | Medium | Medium | This doc is the contract; anything new goes to §4 with a revisit trigger. |

**Open questions (resolve before dev start)**
- [ ] Does DSH expose a user-question primitive the plugin can call synchronously for confirmation, or must class C be hard-deny + `--allow-class-c` only? — Owner: maintainer — needed for M1 design.
- [ ] Is there a clean VM or dedicated Windows account for the eval suite? — Owner: maintainer — blocks M4 credibility.
- [ ] Does the skill fallback still have users? If not, delete it rather than hash-pin it. — Owner: maintainer — simplifies M5.

## 7. What I'd cut if we only got three

If capacity forces a smaller release: **M1 + M4 + M5**. Safety and provability are non-negotiable; refs and batching are leverage that can wait one cycle behind a working, measurable, releasable product. That ordering is a judgment call at ~70% confidence — happy to be argued out of it with eval data showing refs are the binding constraint on task success.
